# Brains Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One storage architecture on every machine, and a remote that hosts many fully separate brains, each the durable copy and sync engine for one user's machines, joined with a share id.

**Architecture:** The machine side keeps files, SQLite and the op log as today; it gains a brain configuration (share hash, remote URL, token), a join flow, and a snapshot bootstrap. The server is rebuilt around a `brain_id` scope: every table and every query is per brain; it materializes current state per `(gid, kind)` from full-state ops, keeps conflict-flagged ops aside until resolved, and never prunes. Naming moves from "endpoint / storage server" to "brain / remote" everywhere a user can see it.

**Tech Stack:** TypeScript, better-sqlite3, vitest, Hono + `@hono/node-server`, Next.js (web), pnpm workspace. `node:crypto` for share ids, token hashes and the machine secret.

**Spec:** `docs/superpowers/specs/2026-10-30-brains-design.md`. Prerequisite: `docs/superpowers/plans/2026-10-30-storage-sync-fixes.md` is fully done (this plan assumes gid-only matching, enqueue-time `base_version`, loser-side forks and resolution ops).

## Global Constraints

- One-line comments only; no em dashes in code, comments, docs or commit messages; no `Co-Authored-By` trailers.
- This ships as **7.0.0** (major architecture change, decided by the user). Task 12 bumps every package version to 7.0.0; `rulesVersion` stays 3.3.0. The unreleased `## 6.2.0` changelog entry is folded into `## 7.0.0 - Brains: one storage architecture, optional remote (YYYY-MM-DD)`; until Task 12, new entries go under that heading in place of 6.2.0.
- The server never imports `kxta-core` and never interprets a payload. Every op kind must be full-state (Task 1 makes tags so).
- Server schema may be reset (no migration from the 6.2.0 `ops`/`clients` layout). Machine-side changes are migrations (`018-brain.sql`).
- Nothing is pruned, on the server or on machines. `acked` outbox rows stay.
- Share id: 32 random bytes; display form Crockford base32, uppercase, 52 characters in groups of 4 separated by `-`; canonical form the raw bytes; the server stores only `HMAC-SHA256(pepper, bytes)`.
- Env vars on the server: `KXTA_RELAY_PEPPER`, `KXTA_RELAY_ENROLL_SECRET`, `KXTA_RELAY_ALLOW_OPEN_CREATE`, `KXTA_RELAY_ALLOW_DEFAULT_PEPPER`, `KXTA_RELAY_DB`, `PORT`, `HOSTNAME`. Package `kontexta-relay`, compose file `docker-compose.relay.yml`, image `kontexta-relay:local`, default DB `/data/kontexta-relay.db`.
- User-facing text says "brain" and "remote". The word "endpoint" disappears from CLI, web, MCP output and README.
- Tests touching files set `KONTEXTA_DATA_DIR` and call `resetDataDirCache()`.

## Review Focus

1. A share id typed with lowercase letters, missing dashes, or `O`/`I` instead of `0`/`1` (Task 2): it must decode to the same bytes (Crockford folds those), so the user can join.
2. A token from brain A sent to any `/brains/*`, `/ops` route while brain B exists with the same gid (Task 3 and Task 14): A must never read or write B's rows; the test asserts 0 cross-brain rows on every route.
3. A join request that times out after the server created the brain but before the client stored the token (Task 9): repeating `connect --share-id` must succeed via the re-join path (new token, same brain), not create a second brain.
4. A replacement machine bootstrapping a brain with unresolved conflicts (Task 10): it must end with the canonical files plus the same conflict copies and conflict rows the other machines have.
5. `tag.set` arriving for a file the machine does not have yet because the create is later in the same page (Task 1): the file create always has a lower seq than any op on its gid, so this cannot happen from the log; the snapshot path (Task 5) must emit a gid's ops in seq order so it cannot happen there either; the test pins snapshot ordering.

### Task 8: Bootstrap and existing-content sync

**Files:**
- Create: `packages/core/src/storage/bootstrap.ts`
- Modify: `packages/core/src/storage/client.ts` (`startSyncLoop` tick: before the first push after a join, run `bootstrapIfNeeded`)
- Test: `packages/core/tests/storage/bootstrap.test.ts`

**Interfaces:**
- `bootstrapIfNeeded(db, opts): Promise<BootstrapResult | null>` runs once per join (flag `settings.brain_bootstrap_pending = 1` set by `joinBrain`, cleared on success) and returns null otherwise.
- Empty machine (no `files` rows): page `GET /brains/snapshot`, apply each gid's `records` through `applyRemoteOp` in order, fork each listed conflict through `forkConflictFromOp`, record versions, set the cursor to `latest_seq`.
- Machine with content: page `GET /brains/snapshot/index`; for each entry: unknown gid → fetch and apply as above; known gid with equal `content_hash` → record version only; known gid with different hash → fork a conflict copy of the remote (fetch its record), keep local; a local file whose path matches a remote record of another gid → `registerPathConflict` (from the sync-fixes plan). Then set the cursor to `latest_seq` and leave the outbox to the normal push (local history goes up with enqueue-time bases, which the server flags correctly).
- Resumable: progress is kept in `settings.brain_bootstrap_after` (last gid processed); a rerun continues from it.
- `BootstrapResult { mode: "empty" | "merge"; applied: number; forked: number; cursor: number }`
